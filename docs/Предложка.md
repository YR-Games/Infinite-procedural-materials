# Архитектура системы "Запросов и предложений"

Ниже представлен концептуальный проект системы, аналогичной GitHub Issues, где «Issue» = «Запрос». Технологии и SQL-схемы не фиксируются; описаны домен, объекты фронтенда/бэкенда, сущности БД и связи.

## 1. Назначение и роли

Система позволяет вести запросы внутри проектов, обсуждать их, отдельно вести комментарии разработчиков, собирать пожертвования на конкретный запрос и сортировать список запросов по приоритету и превышению целевого сбора.

Роли:

- Гость — просмотр публичных запросов, пожертвования, чтение комментариев.
- Пользователь — создание запросов/комментариев/пожертвований в рамках прав проекта.
- Разработчик проекта — может писать в отдельный блок комментариев разработчиков, предлагать смену приоритетов.
- Мейнтейнер/владелец — управляет приоритетом, целевой суммой, статусами, метками, назначениями.

## 2. Ключевые бизнес-правила

1. Каждый запрос принадлежит проекту.
2. У запроса есть:
   - изначальный приоритет — числовой `base_priority_score` (по умолчанию __1__);
   - целевая сумма сбора `target_amount` (по умолчанию __5000__ р.);
   - фактически собранная сумма `collected_amount`;
   - процент превышения цели `overfunding_percent`;
   - вычисляемый рейтинг сортировки `rank_score`.
3. Пожертвовать можно любую положительную сумму в валюте запроса. Анонимные пожертвования разрешены.
4. В `collected_amount` учитываются только успешные пожертвования. `Pending`/`failed`/`refunded` не учитываются или вычитаются при возврате.
5. У запроса два независимых блока обсуждения:
   - обычные комментарии;
   - отдельный блок комментариев разработчиков, визуально выделенный и хранимый отдельно.
6. В блок разработчиков может писать только участник проекта с ролью разработчика/мейнтейнера/владельца.
7. Сортировка списка:

   ```python
   overfunding_percent = max(-1, (collected_amount - target_amount) / target_amount * 100)
   rank_score = base_priority_score + overfunding_percent + (date.now-date.day) // 30
   ```

   Если цель не превышена, `overfunding_percent` в интервале `[-1, 0)`. Сортировка по `rank_score` по убыванию; тай-брейк — `base_priority_score`, затем дата создания.
   > Ранг тем выше, чем выше изначальный приоритет, чем больше собранная сумма и чем больше месяцев существует запрос.
8. Пересчёт `overfunding_percent` и `rank_score` выполняется при успешном пожертвовании, возврате, изменении целевой суммы или приоритета.
9. Запрос может быть закрыт мейнтейнером/владельцем. Закрытый запрос перестаёт отображаться в общем списке и навсегда удаляется через `4 месяца` с момента закрытия.

## 3. Сущности БД и связи

### Основные сущности

| Сущность | Назначение | Ключевые атрибуты | Связи |
| --- | --- | --- | --- |
| `User` | Пользователь | id, login, email, display_name, avatar, status | 1-N Project как владелец; N-M Project через ProjectMember; 1-N Comment, DeveloperComment, Donation |
| `Project` | Проект/репозиторий | id, owner_id, name, slug, description, visibility, currency | N-1 User; 1-N Issue, Label, ProjectMember |
| `ProjectMember` | Участие пользователя в проекте | id, project_id, user_id, role, joined_at | N-1 Project; N-1 User; уникальность project_id+user_id |
| `Issue` | Запрос | id, project_id, number, title, description, status_id, base_priority_score, priority_label, target_amount, currency, collected_amount, overfunding_percent, rank_score, created_by_id, created_at, updated_at, closed_at | N-1 Project; N-1 IssueStatus; N-1 User как автор; 1-N Comment, DeveloperComment, Donation; N-M Label; N-M User как assignee |
| `IssueStatus` | Статус запроса | id, project_id, name, category: open/closed, order | 1-N Issue |
| `Label` | Метка | id, project_id, name, color | N-1 Project; N-M Issue через IssueLabel |
| `IssueLabel` | Связь запроса и метки | issue_id, label_id | N-1 Issue; N-1 Label |
| `IssueAssignee` | Назначенные исполнители __Возможно не люди, а команды???__ | issue_id, user_id | N-1 Issue; N-1 User |
| `Comment` | Обычный комментарий | id, issue_id, author_id, parent_comment_id, body, created_at, updated_at, deleted_at | N-1 Issue; N-1 User; самосвязь parent_comment_id |
| `DeveloperComment` | Комментарий разработчика | id, issue_id, author_id, body, visibility, created_at, updated_at, deleted_at | N-1 Issue; N-1 User; автор обязан быть ProjectMember с ролью разработчика/мейнтейнера/владельца |
| `Donation` | Пожертвование на запрос | id, issue_id, donor_user_id, amount, currency, status, anonymous, idempotency_key, created_at, paid_at | N-1 Issue; N-1 User опционально; 1-N PaymentTransaction |
| `PaymentTransaction` | Попытка платежа | id, donation_id, provider, external_id, amount, currency, status, raw_payload, created_at, updated_at | N-1 Donation |
| `Attachment` | Вложение | id, owner_type, owner_id, filename, url, uploaded_by_id | Полиморфно к Issue/Comment/DeveloperComment; N-1 User |
| `Notification` | Уведомление | id, user_id, type, payload, read_at, created_at | N-1 User |
| `AuditLog` | Аудит действий | id, actor_id, entity_type, entity_id, action, payload, created_at | N-1 User |

### Полный перечень связей

- `User 1-N Project` — владелец проекта.
- `User N-M Project` — через `ProjectMember`.
- `Project 1-N Issue`.
- `Project 1-N Label`.
- `Issue N-M Label` — через `IssueLabel`.
- `Issue N-M User` — через `IssueAssignee`.
- `Issue N-1 IssueStatus`.
- `Issue 1-N Comment`.
- `Issue 1-N DeveloperComment`.
- `Issue 1-N Donation`.
- `Donation N-1 User` — донор опционален.
- `Donation 1-N PaymentTransaction` — несколько попыток платежа.
- `User 1-N Comment`.
- `User 1-N DeveloperComment`.
- `User 1-N Donation`.
- `Comment 1-N Comment` — опциональная ветка ответов.
- `Attachment` — полиморфная связь с Issue/Comment/DeveloperComment.
- `Notification N-1 User`.
- `AuditLog N-1 User`.

Ограничения:

- `ProjectMember(project_id, user_id)` уникально.
- `Issue(project_id, number)` уникально.
- `IssueLabel(issue_id, label_id)` уникально.
- `IssueAssignee(issue_id, user_id)` уникально.
- `Donation.idempotency_key` уникален.
- `PaymentTransaction(provider, external_id)` уникально.
- `target_amount > 0`, `Donation.amount > 0`.

## 4. Объекты фронтенда

### Страницы/маршруты

- Список запросов проекта.
- Детальная страница запроса.
- Создание/редактирование запроса.
- Модальное окно пожертвования.
- Страница/раздел «Мои пожертвования»/профиль.
- Авторизация.

### Компоненты

- `IssueList` — список с сортировкой по `rank_score`.
- `IssueCard` — карточка запроса: приоритет, статус, метки, собранная сумма, цель, прогресс, процент превышения.
- `IssueDetail` — детальная информация.
- `FundingSummary` — сумма собранных пожертвований и целевая сумма.
- `FundingProgressBar` — прогресс достижения цели.
- `OverfundingBadge` — процент превышения цели.
- `DonationButton` / `DonationModal` / `DonationForm` — сумма, анонимность, способ оплаты, валидация.
- `CommentsPanel` — обычные комментарии.
- `DeveloperCommentsPanel` — отдельный визуально выделенный блок комментариев разработчиков.
- `DeveloperCommentForm` — доступен только разработчикам/мейнтейнерам.
- `PriorityBadge`, `StatusBadge`, `LabelList`, `AssigneeList`.
- `SortControl` — отображает текущую сортировку и компоненты рейтинга.
- `PermissionGuard` — скрытие/блокировка действий по ролям.

### Модели/состояния фронтенда

- `IssueListItem`: id, title, status, basePriority, collectedAmount, targetAmount, overfundingPercent, rankScore, labels.
- `IssueDetail`: полный запрос + блоки комментариев + донаты.
- `DonationFormState`: amount, currency, anonymous, paymentMethod, status.
- `CommentListState`, `DeveloperCommentListState`.
- `AuthState`, `ProjectPermissionsState`.

### Правила UI

- В списке по умолчанию сортировка по `rank_score DESC`.
- На карточке явно показываются `collected_amount`, `target_amount`, `overfunding_percent`.
- Блок разработчиков всегда отделён от обычных комментариев и имеет отдельный заголовок/стиль. Отображается только если не пуст.
- Кнопка пожертвования доступна на карточке и детальной странице.
- Ошибки платежа и статусы `pending` отображаются отдельно.

Концептуальные endpoints:

- `IssueService` — управление запросами.

- `FundingService` — агрегация успешных донатов.
- `DonationService` — создание доната, идемпотентность, статусы.
- `PaymentService` — интеграция с провайдером, обработка вебхуков.
- `CommentService` — обычные комментарии.
- `DeveloperCommentService` — проверка роли автора и ведение отдельного блока.
- `PermissionService` — проверка прав.

### Репозитории

- `IssueRepository`, `DonationRepository`, `CommentRepository`, `DeveloperCommentRepository`, `ProjectMemberRepository`, `PaymentTransactionRepository`.

### Фоновые задачи/события

- `DonationSucceeded` → увеличить `collected_amount`, пересчитать рейтинг.

## 6. Сценарии

### Пожертвование

1. Пользователь открывает запрос.
2. Видит цель, собранную сумму, прогресс и процент превышения.
3. Вводит любую положительную сумму.
4. Создаётся `Donation` в статусе `pending` и `PaymentTransaction`.
5. После успешного вебхука донат становится `succeeded`.
6. `collected_amount` увеличивается атомарно.
7. `RankingService` пересчитывает `overfunding_percent` и `rank_score`.
8. Список запросов при следующем чтении сортируется по новому рейтингу.

### Комментарии разработчиков

1. Пользователь с ролью разработчика открывает запрос.
2. Видит отдельный блок `DeveloperCommentsPanel`.
3. Оставляет комментарий через отдельный endpoint.
4. `DeveloperCommentService` проверяет членство в проекте и роль.
5. Комментарий сохраняется отдельно от обычных комментариев.

### Сортировка списка

1. Пользователь открывает список запросов.
2. Бэкенд возвращает элементы с `base_priority_score`, `overfunding_percent`, `rank_score`.
3. Сортировка: `rank_score DESC`, затем `base_priority_score DESC`, затем `created_at ASC`.
4. Фронтенд показывает и итоговый рейтинг, и его составляющие.

## 7. Итоговая концептуальная схема

`Project` содержит `Issue`. `Issue` имеет один `IssueStatus`, много `Comment`, много `DeveloperComment`, много `Donation`, много `Label` через `IssueLabel`, много `User` через `IssueAssignee`. `Donation` принадлежит `Issue` и опционально `User`, имеет много `PaymentTransaction`. `DeveloperComment` принадлежит `Issue` и `User`, но автор обязан быть участником проекта с ролью разработчика. Список запросов сортируется по формуле «изначальный приоритет + процент превышения целевой суммы сбора».
